### FINDING 1: Cross-Environment JWKS Key Reuse (4 Identity Hosts)

| Q | Answer |
|---|---|
| Q1 Scope? | **YES** — `connect.signl4.com`, `devconnect.signl4.com`, `api.signl4.com`, `devapi.signl4.com` all `.signl4.com` = in-scope SaaS/product infrastructure |
| Q2 Reachable? | **YES** — public OIDC discovery + JWKS endpoints, unauthenticated |
| Q3 Impact? | **YES** — single RS256 key shared across staging+prod means key compromise in any env = token forgery in all envs; cross-tenant risk |
| Q4 Provable? | **YES** — passive JWKS fetch, byte-compare kid/n/x5t/x5c across 4 hosts; 10+ deep-equal observations logged |
| Q5 Novel? | **YES** — not a generic single-instance JWT alg confusion; this is cross-environment key sharing across 4 separate IdentityServer instances |
| Q6 Always-rejected? | **NO** — not DoS, not stack trace, not headers, not outdated lib |
| Q7 Reasonable triager? | **YES** — real key management weakness with token forgery chain (blocked on client_secret, but key reuse itself is the defect) |

**Verdict: VALID**

**Proof steps (read-only):**
1. `curl -s https://connect.signl4.com/.well-known/openid-configuration | jq .jwks_uri` → fetch JWKS

3. Repeat for `devconnect.signl4.com`, `api.signl4.com`, `devapi.signl4.com` — same kid, n, x5t, x5c

**Impact:** Medium-High — key compromise in staging → token forgery in production; cross-tenant risk if keys overlap with customer IdPs
**CVSS 3.1:** 7.4 (AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N)
